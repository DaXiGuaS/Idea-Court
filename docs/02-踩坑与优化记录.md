# 项目踩坑与优化记录

记录开发过程中真实遇到的问题、当时的判断、以及最后的处理方式。
有些判断一开始是错的，后来被实测推翻，这些也如实写下来。

---

## 一、五个角色像五个复读机

### 现象

第一版提示词只写了一句：

```
你现在是 5 个不同的评审，分别从产品、技术、测试、商业、用户的角度质疑我的想法。
```

结果五条发言全是同一个意思：

- 产品经理：这个想法没意思
- 后端：这个想法没意思
- 测试：这个想法没意思
- ……

措辞不同，论点完全一样。

### 我的分析

单模型分饰多角时，如果没有硬约束，模型会倾向输出「安全的平均答案」。
角色名字只是个标签，没有改变它的推理路径。

调温度没用——温度只影响随机性，不改变「五个角色共享同一套判断标准」这件事。

### 解决方案

给每个角色绑定**唯一维度**，并明确写出**禁止越界**：

```python
{
    "name": "后端工程师·老陈",
    "dimension": "工程可行性",
    "only_ask": "数据从哪来？量大了撑得住吗？出故障了谁兜底？",
    "never_ask": "不要聊用户体验，不要谈赚钱",
}
```

关键在于 `never_ask`。只写「你负责技术」不够，必须写「**不许**谈钱、**不许**聊用户」，
模型才会真正收窄。

### 效果

同一个想法，五条发言的关注点完全不同：数据来源、异常分类、付费意愿、使用习惯、摊薄成本——
每条都能单独拿出来看。

## 二、DeepSeek 的 function calling 不可靠，踩了两次

### 第一次：`json_schema` 直接被拒

按照 LangChain 1.x 的默认用法写：

```python
structured = llm.with_structured_output(ReviewResult)
```

接口返回 400：

```
This response_format type is unavailable now
```

原因是 LangChain 1.x 的 `with_structured_output` 默认 `method="json_schema"`，
会发送 `response_format: {"type": "json_schema"}`，而 DeepSeek 的兼容接口不支持这个类型。

**第一次修复**：显式改成 `method="function_calling"`。

### 第二次：调用成功，但解析结果是 None

改完 function calling 后，第一次调用 200 成功，token 也记录到了（1756），
但 `parsed` 是 `None`。

排查发现：模型这次没有调用工具，`finish_reason` 是 `stop` 而不是 `tool_calls`。

**这个错误是偶发的**——同一天重跑，有一次成功、有两次连续失败。
说明 DeepSeek 对 function calling 的触发并不稳定，`tool_choice` 默认是 `auto`，
模型可以自己决定「不调用工具、直接回答」。

### 最终方案：JSON mode + Pydantic 手动校验

放弃 `with_structured_output`，改成：

```python
llm = build_llm().bind(response_format={"type": "json_object"})
message = llm.invoke(messages)
data = _extract_json(message.content)   # 容忍 ```json 包裹和前后干扰文字
result = ReviewResult.model_validate(data)
```

配合两件事：

1. 提示词里写死输出格式和字段说明
2. 校验失败时重试，最多 2 次

### 效果

之后连续多次调用没有再出现解析失败。代价是要自己写 JSON 提取和校验，
但链路完全可控，出问题时能定位到「是模型没按格式输出」还是「是网络/接口错误」。

## 三、温度 0.8 让投票随机跳动

### 现象

一开始为了让五个角色语气差异更明显，把温度设成 0.8。

结果是：**同一段输入、同样的反驳，跑两次的票数不一样。**

- 第一次：0 支持 / 0 反对 / 0 有条件 → 第一轮全反对
- 反驳后：0 / 1 / 4（有条件通过）
- 再跑一次：0 / 4 / 1（驳回）

### 我的分析

温度高不只影响措辞，也影响判断。五个角色是独立生成的，
每一个人投票时都在掷骰子，五个骰子叠加，结果自然不稳。

而「语气差异」其实应该靠提示词里写死的人设来保证，不该指望温度。

### 解决方案

- 温度从 0.8 降到 **0.4**
- 语气差异继续由 `style` 字段保证（「语速快、没耐心、爱反问」这类描述）

### 效果

降到 0.4 后，两次运行的票数完全一致（0 / 4 / 1）。

**副作用**：翻盘变难了。高温时靠运气偶尔能翻，低温下必须真的把五个问题都答上。
这说明之前那次「翻盘」是随机波动，不是设计出来的效果。

## 四、角色会临时发明新质疑

### 现象

用户反驳后，某个角色明明投了 `conditional`（说明已经被部分说服），
但只要用户没有回应到它的另一个问题，下一轮它又把票改回 `reject`，
而且问的是**上一轮已经问过、用户也已经回答过的问题**。

用户视角就是：「我说了，你不听，你还在挑刺。」

### 我的分析

这不是模型坏，是提示词没有约束「改票的公平性」。
真实的评审会不会这样——你回答了，对方要么认，要么提出**新的**依据。

### 解决方案

在铁律里加两条：

```
7. 如果对方已经正面回应了你的核心质疑，你必须改票，
   不许临时发明新的质疑，也不许把已经回应过的问题再问一遍。
8. 如果你上一轮投了 conditional 或 approve，本轮除非对方引入了明显的新漏洞，
   否则只能维持原票或上调，不许改回 reject。
```

### 效果

有明显改善，但不是 100%。模型仍偶尔重复旧问题——
这类约束只能降低概率，不能根除，后续用「投票只看自己维度」再收一次（见下一条）。

## 五、投票被别的维度带偏

### 现象

用户明明已经回答了产品经理的问题，产品经理仍然投 `reject`。
看它的理由，写的是「老板说这个没商业价值」。

问题在于：**产品经理在为老板的维度投票。**

### 我的分析

铁律里只写了「每个角色只从自己的维度质疑」，
但投票那一步写的是「vote 取决于这个想法是否站得住」——
「站得住」是整体判断，不是维度判断。角色自然地扩大了权限。

### 解决方案

把投票标准也限定到维度内：

```
5. 投票只看你自己的维度，不要因为别的维度有问题就跟着投 reject：
   - 你的核心问题被正面回答了 → 至少投 conditional
   - 你的核心问题被回答得很好、没有明显漏洞 → 投 approve
   - 你的核心问题被回避了、或者答案是空的 → 投 reject
```

### 效果

配合全覆盖的反驳，票数能从 0/5/0 变成 0/2/3（有条件通过）。
前提是用户真的把大部分维度都答上了——这也符合「评审应该严格」的预期。

## 六、中文引号让整个前端失效

### 现象

改完预置案例后，页面能打开（HTTP 200），但**所有交互失效**：
点按钮没反应，不弹评审。

### 我的分析

浏览器控制台没有直接看，但用 node 做了语法检查：

```
SyntaxError: Unexpected identifier '使用者不是付费者'
```

原因是一行 JS 字符串用了英文双引号嵌套：

```js
desc: "看看"使用者不是付费者"会怎么被打",
```

里面的中文引号被我写成了英文 `"`，字符串提前结束，整个 `<script>` 解析失败。
JS 不会局部报错，而是整块不执行——所以页面「能打开但全是死的」。

### 解决方案

- 改用中文引号「」，或统一用单引号包裹
- 加了一步固定检查：把 `<script>` 抽出来跑 `node --check`

### 效果

之后每次改前端都先跑一次语法检查，这类问题在打开浏览器之前就能发现。

## 七、`start.bat` 找不到：中文文件名 + cmd 内置命令

### 现象

做好启动脚本后，在 Git Bash 里测试：

```
'启动.bat' 不是内部或外部命令
```

换成英文名 `start.bat` 后，仍然报同样的错。

### 我的分析

两层问题叠在一起：

1. **中文文件名**：Git Bash 调用 `cmd` 时，参数编码在 UTF-8 和 GBK 之间转换，路径传过去已经乱了
2. **`start` 是 cmd 的内置命令**：即使文件名正确，`start.bat` 也可能被解析成内置命令 `start` + 参数

### 解决方案

- 文件名改成 **`run.bat`**，避开中文编码和内置命令冲突
- 用完整路径调用验证

### 效果

`run.bat` 用完整路径执行成功，服务正常返回 200。

**补充**：用户双击时走的是资源管理器（完整路径），本来就不会遇到上面的问题；
真正踩坑的是我自己的命令行验证方式。但改成 `run.bat` 更稳妥，没有坏处。

## 八、总结：哪些是设计，哪些是妥协

| 问题 | 处理方式 | 性质 |
|---|---|---|
| 角色同质化 | 唯一维度 + 禁止越界 | 设计 |
| function calling 不稳 | 改 JSON mode + 校验 + 重试 | 妥协 |
| 票数随机 | 降温度 + 维度独立投票 | 设计 |
| 角色反复变脸 | 铁律约束 | 部分解决 |
| 前端整页失效 | 语法检查流程 | 工程习惯 |
| 启动脚本冲突 | 改名 | 工程细节 |

有一条诚实的结论：**这个项目的「翻盘」不是随机给的**。
温度降低后，用户必须真的把大部分问题回答清楚才能改变判决。
这不是 bug，是它想做的事——逼你把没想清楚的地方想清楚。
